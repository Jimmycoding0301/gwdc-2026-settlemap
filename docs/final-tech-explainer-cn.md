# SettleMap · 技术原理人话版

这份稿对应五分钟路演的九个时间点。每一段先给出可以直接说的话，再解释背后的技术。

## 1. 0:00 · 换址、历史重复、超时双付

### 上台直接说

运营付款前有三个高风险。第一，同一个收款人突然换了钱包，可能是正常换址，也可能是抄错、OCR 识别错或账号被冒用。第二，同一条内容或业务单可能已经付过。第三，浏览器没收到结果，不代表付款失败；如果服务商其实已经受理，再点一次就可能双付。

SettleMap 会比较历史地址、检查业务单历史，并把没有明确结果的付款标成 UNKNOWN。UNKNOWN 会暂停队列，不允许直接重付。

### 背后的原理

- **地址校验**：TRON 地址带 Base58Check 校验码，能发现很多字符输入错误，但它不能证明地址属于谁。地址变化仍然需要人在原聊天渠道确认。
- **历史查重**：业务单号或内容编号会与已结算、处理中和待核查记录比较。已付或结果不明的业务都不能再次进入新批次。
- **防双付状态机**：只有服务商明确返回失败，才叫 `FAILED`。网络断开或页面超时只能叫 `UNKNOWN`，系统必须先查旧请求。

## 2. 0:25 · 12 行变成 9 行，再变成 3 笔

### 上台直接说

演示从 12 条原始业务开始。运营先修正一条 OCR 地址错误，并人工复核一条地址变化；历史已付、重复业务单和未确认的大额异常继续隔离，因此留下 9 条可以付款的业务。随后只把收款人身份、钱包地址和币种完全一致的业务合并，最终生成 3 笔付款。

合并只减少链上付款次数，不会删除原始业务。每笔付款都保存它对应的业务行和内容编号，所以付款完成后仍能逐行回填。

### 背后的原理

- **分组键**：使用稳定的收款人 ID、完整钱包地址和币种共同分组。只看昵称不安全，同名的人可能不是同一个人。
- **逐行映射**：每个付款对象保存原始 `rowId` 和 `invoiceId`。一笔合并付款可以反查它结算了哪几行。
- **整数金额**：金额先换算成最小单位计算，`1 USDT = 1,000,000 micro-USDT`，避免计算机小数造成几分钱或几微单位的误差。
- **确定性清单**：相同输入会生成相同的清单摘要。地址、金额或人工处理决定变化后，旧摘要失效，必须重新确认。

可以把它理解成：9 张报销单装进 3 个付款信封。信封少了，但每个信封里的装箱清单还在。演示里的手续费节省使用固定 fixture 费率，不代表 GasFree 的真实固定费率。

## 3. 0:50 · 业务行为什么会失去身份，超时为什么不等于失败

### 上台直接说

链上交易通常只显示从哪个地址、向哪个地址、转了多少钱。它不知道这笔钱对应哪条内容、哪张发票，也不知道运营人员做过什么复核。

SettleMap 在本地保留一张关系表，把业务行、付款组、服务商追踪编号和链上交易重新连接起来。网络超时时，系统不会猜测成功或失败，而是停止后续付款并查询原来的追踪编号。

### 背后的原理

- **链上信息有限**：TRC-20 Transfer 事件主要记录 token、from、to 和 amount，不包含公司的业务单号。
- **本地 manifest**：manifest 是付款清单的确定性摘要，用于发现本地参数被改动，并连接业务行与付款组。它没有上链，也没有被钱包签名。
- **UNKNOWN 与 FAILED 分开**：`FAILED` 是已经得到明确失败结果；`UNKNOWN` 是证据不足。把二者混为一谈是重复付款的来源。即使明确失败，系统也不会自动重付，仍需重新复核和授权。

## 4. 1:20 · Review、Group、Authorize、Recover

### 上台直接说

Review 是先检查地址、金额、重复业务和历史付款。Group 是把相同收款人、相同地址、相同币种的业务合并，但保留逐行关系。Authorize 是用户在 TronLink 里核对结构化付款内容并签名，私钥不离开钱包。Recover 是付款结果不确定时查询原来的 GasFree trace，再用 Nile 节点核验最终结果。

### 背后的原理

- **Review**：确定性代码负责安全规则，OCR 只生成待确认草稿，不能自动授权付款。
- **Group**：合并前后都绑定收款人、地址、币种和金额，避免把不同付款误合并。
- **Authorize**：实时模式先重读余额、冻结金额、nonce、动态费用和授权期限，再使用 TIP-712 结构化签名。它像一张写明收款人、金额、最高费用和失效时间的电子付款许可。产品浏览器路径由 TronLink 签名，后端不请求钱包私钥或助记词；服务端 HMAC 只证明 API 请求来自获准应用，不能代替钱包授权。
- **Recover**：服务端持久化 `requestId` 和 `traceId`。有 trace 时只查同一次尝试，不创建第二次 submit；如果连 trace 都没有，只能冻结并人工核查。

## 5. 1:40 · 67 秒 Demo 为什么使用 fixture

### 上台直接说

视频中的三笔流程是本地 fixture，也就是可重复的故障演练。系统故意让第二笔在服务端保存 trace 后丢失浏览器响应，从而稳定展示 UNKNOWN、暂停队列和恢复原请求。它不转真实 USDT，也不生成真实交易哈希。

### 背后的原理

- **Fixture**：固定输入和固定故障条件，保证每次演示得到同样结果，避免现场网络决定 Demo 成败。
- **故障注入**：系统故意模拟“服务端已受理、浏览器没收到响应”，这是最容易引发双付的真实故障模式。
- **证据分层**：fixture 证明产品在异常情况下如何处理；独立 canary 证明真实 GasFree 写入链路确实跑通过。两者不能互相替代。

所有 `sim_` 开头的 request、trace 和 hash 都是模拟编号，不是链上证据。

## 6. 2:47 · SUCCEED、SOLIDITY、block 71389721、log 2

### 上台直接说

真实 canary 需要两层证据。`SUCCEED` 是 GasFree 服务商说这次请求执行成功；`SOLIDITY` 是 Provider 报告交易已经进入 TRON 的固化状态。SettleMap 随后再独立查询 Nile Solidity RPC，不只相信 Provider 自己的状态。

区块 `71389721` 相当于这笔交易在账本中的页码。`log 2` 是交易回执中编号为 2 的事件记录。系统在这条 Transfer 事件里再次核对代币、付款地址、收款地址和精确金额。服务商结果与链上结果同时一致，系统才标记确认。

### 背后的原理

- **Provider SUCCEED**：证明 GasFree 根据 trace 找到了成功结果，但不能单独证明链上内容完全符合本地清单。
- **Chain SOLIDITY**：表示 TRON Solidity 节点已经看到固化后的交易结果，比只看到刚广播的交易更可靠。
- **Block number**：区块高度用于定位交易被确认的位置。
- **Log index 2**：事件索引从 0 开始，`2` 是该交易回执中的第三条日志。它让系统精确定位目标 TRC-20 Transfer。
- **独立 RPC 核验**：应用不只相信 Provider，还直接向 Nile Solidity RPC 读取交易、回执和事件，匹配 token、from、to 与整数金额。
- **余额与调用次数复核**：GasFree 地址共减少 `2.300001 USDT`，刚好等于转账 `1.000001` 加实际费用 `1.3`；广播接口只调用一次。这些是同一笔 canary 的交叉证据，不是第二笔付款。

## 7. 3:35 · 非托管 SaaS

### 上台直接说

目标用户是反复给创作者、活动人员或供应商付款的运营团队。SettleMap 是非托管 SaaS：我们提供导入、复核、恢复和对账软件，但不替客户保管私钥或资金。用户仍然通过自己的钱包授权。

商业上可以按团队工作区、月度批次量和 Sheets 或 ERP 连接器收费。

### 背后的原理

- **非托管**：产品设计中，应用不掌握能直接转走用户资金的私钥，用户在自己的钱包里决定是否签名。当前真实 canary 使用受控的一次性测试工具和本地测试私钥完成，因此它不等于浏览器 TronLink 已端到端验证。
- **SaaS**：客户为持续使用的软件服务付订阅费，而不是把资金交给 SettleMap 代管。
- **GasFree 不是零费用**：用户无需另外准备 TRX，但服务费用仍然存在，并可从 USDT 中支付。

## 8. 4:05 · 一笔 canary 与完整批量的边界

### 上台直接说

Canary 就像矿井里的金丝雀，是一笔金额很小、参数已知的真实探针交易。这里使用独特金额 `1.000001 USDT`，方便在链上精确识别，并核对了 `1.3 USDT` 实际费用。

它证明单收款人的 GasFree 鉴权、TIP-712 签名、提交、trace、链上固化、Transfer 日志和费用复核已经跑通。但它不能证明刚才的三笔 fixture 已经上链，也不能证明浏览器 TronLink 的完整批量流程已经端到端验证。

### 背后的原理

- **唯一金额**：`1.000001` 比整数金额更容易在测试记录中准确对应目标交易。
- **单收款人范围**：只有一个 receiver，因此没有验证多收款人的串行队列和逐笔签名。
- **真实链路范围**：验证的是 GasFree Provider 到 Nile，再到独立 RPC 核验的链路。
- **尚未证明的部分**：多收款人真实批次、浏览器 TronLink 全流程，以及真实批次导出的逐行业务对账包。
- **批次不是一笔原子交易**：这里的批次是业务层的一组付款。真实实现仍要逐笔预检、逐笔签名并串行执行。

## 9. 4:45 · 每条业务有处置结果；不确定时绝不盲目重付

### 上台直接说

“每条业务有处置结果”是指每一行最终都有付款 ID、状态和链上交易，或者明确的暂缓原因。如果已经拿到 trace，系统只查询原 trace；如果响应在 trace 返回前就丢失，系统锁住这张付款单并转人工核对，绝不猜测失败后再付一次。

Trace 就像快递单号。快递状态没更新时，正确做法是查询原来的单号，而不是再寄一件。SettleMap 用同样的方法避免重复付款。

### 背后的原理

- **Request ID**：应用提交前生成的诊断编号，但它本身不是可靠的幂等保证，当前官方接口也不能按它反查付款结果。
- **Trace**：GasFree Provider 接受付款后返回的追踪标识，用于继续查询同一次尝试。
- **行级回填**：付款结果通过 payment ID 映射回原始行，形成业务 CSV 和付款 CSV 两层记录。
- **安全恢复**：有 trace 时，恢复操作只读取原 trace 的状态，不创建新授权或第二次提交，因此 attempt 数不会增加；没有 trace 时，当前只能锁单并人工向 Provider 核对。

最终收尾建议直接说：**“每条业务都有处置结果；有 trace 就只追原 trace，没有 trace 就锁单人工核对，绝不盲目付第二次。”**

## 一分钟术语速记

- `UNKNOWN`：不知道成功还是失败，所以暂停并查询。
- `FAILED`：已经得到明确失败结果。
- `traceId`：服务商给这一次付款的快递单号。
- `requestId`：应用提交前生成的诊断编号，不等于幂等保证。
- `TIP-712`：让钱包展示并签署结构化付款内容的标准。
- `manifest`：本地付款清单摘要，用于发现参数被改动；没有上链。
- `SUCCEED`：GasFree Provider 报告成功。
- `SOLIDITY`：TRON Solidity 节点看到交易已经固化。
- `RPC`：程序向区块链节点查询交易和回执的接口。
- `block`：交易所在的区块高度，类似账本页码。
- `log`：智能合约执行产生的事件记录。
- `canary`：范围很小、参数已知的真实探针测试。
- `fixture`：固定数据和固定故障的可重复本地演示。
- `non-custodial`：产品不保管用户私钥和资金。
